# Система бронирования билетов в театр

В этом проекте вам предстоит создать небольшую систему, которая помогает театру управлять билетами: учитывать свободные места, бронировать и продавать билеты, рассчитывать стоимость и собирать статистику по спектаклю.

Задание построено поэтапно. Сначала вы опишете основные сущности и правила, затем добавите операции для работы с билетами, а в конце подготовите отчёты и разберёте более сложные сценарии бронирования.

## Чему вы научитесь

Во время работы над проектом вы потренируетесь:

- переводить описание реального процесса в понятную модель;
- задавать и проверять бизнес-правила;
- работать с наборами данных: искать, отбирать, группировать и изменять элементы;
- передавать правила отбора и расчёта в качестве параметров;
- обрабатывать ошибочные ситуации без частичного изменения данных;
- формировать сводную статистику и человекочитаемые отчёты;
- разбивать большую задачу на небольшие последовательные этапы.

## Как начать

Проект пишется на Kotlin, сборка через Gradle уже настроена. Свой код размещайте в каталоге `src/main/kotlin`, начиная с функции `main`. Запускать программу удобнее всего из IDE (IntelliJ IDEA). При желании добавляйте автотесты в `src/test/kotlin` — необходимые зависимости уже подключены, запуск командой `./gradlew test`.

Если какой-то приём Kotlin вам ещё незнаком, загляните в раздел «Подсказки» в конце документа.

## Предметная область

Система работает со спектаклями и билетами на них.

Для спектакля нужно хранить:

- название;
- дату и время проведения;
- место проведения.

Для каждого билета нужно хранить:

- уникальный идентификатор;
- номер места;
- категорию места;
- базовую стоимость;
- текущее состояние;
- спектакль, к которому относится билет.

В театре есть три категории мест:

| Категория | Как влияет на базовую стоимость |
| --- | ---: |
| Партер | увеличивает в 1,5 раза |
| Балкон | не изменяет |
| Ложа | увеличивает в 2 раза |

Итоговая цена билета должна рассчитываться с учётом его категории. Например, билет в партер с базовой стоимостью 1000 рублей стоит 1500 рублей.

Чтобы не путаться в терминах, дальше по тексту:

- **базовая стоимость** — цена до применения множителя категории;
- **итоговая цена** — цена после применения множителя категории (и скидки, если она есть).

## Жизненный цикл билета

Билет может находиться в одном из четырёх состояний:

- **доступен**: билет можно забронировать или купить;
- **забронирован**: билет временно закреплён за покупателем;
- **продан**: покупка завершена;
- **отменён**: билет больше нельзя использовать.

Состояние нельзя менять произвольно. Соблюдайте следующие правила:

| Текущее состояние | Допустимые следующие состояния |
| --- | --- |
| Доступен | забронирован, продан или отменён |
| Забронирован | доступен, продан или отменён |
| Продан | отменён |
| Отменён | переходов нет |

Если операция нарушает эти правила, система должна отклонить её и сообщить понятную причину. Способ сообщения выберите сами: например, выбрасывать исключение с понятным текстом или возвращать результат вида «успех или ошибка». Главное — чтобы после отказа данные оставались в прежнем состоянии.

## Этап 1. Подготовьте данные

Создайте один спектакль и 15 билетов на него. Для всех билетов задайте одинаковую базовую стоимость — 1000 рублей. Итоговая цена определяется множителем категории:

- 5 билетов в партер — итоговая цена каждого 1500 рублей;
- 5 билетов на балкон — итоговая цена каждого 1000 рублей;
- 5 билетов в ложу — итоговая цена каждого 2000 рублей.

Итоговую цену вычисляйте из базовой стоимости и множителя категории, а не задавайте готовым числом.

Используйте разные номера мест и уникальные идентификаторы, например вида `T001`, `T002` и так далее. В начале все билеты могут быть доступны, а затем часть из них можно перевести в другие состояния для проверки сценариев.

## Этап 2. Реализуйте основные операции

### Поиск билетов

Добавьте возможность находить билеты по произвольному условию. Условие должно передаваться в операцию снаружи — как параметр, а не быть жёстко записанным внутри кода. Тогда одна и та же операция поиска позволит, например:

- найти все доступные билеты в партере;
- найти все забронированные билеты;
- найти билеты, итоговая цена которых ниже указанной суммы.

Подсказка: в Kotlin условие удобно передавать лямбдой — функцией, которая получает билет и возвращает `true` или `false` (подробнее — в разделе «Подсказки»).

### Массовое изменение

Добавьте возможность выбрать несколько билетов по условию и выполнить с каждым из них одно действие. Как и условие поиска, действие передаётся в операцию как параметр. Проверьте эту возможность на следующих примерах:

- отменить все забронированные билеты;
- перевести выбранные билеты в другую категорию, например переместить билеты с балкона в партер;
- снять броню со всех билетов, удовлетворяющих заданному условию.

Все изменения состояния должны подчиняться правилам жизненного цикла билета.

### Правила расчёта цены

Предусмотрите возможность создавать разные правила ценообразования. Правило должна создавать отдельная операция: она получает размер скидки и возвращает готовое правило, которое затем можно применять к любым билетам. Для начала достаточно скидки, заданной долей от итоговой цены — числом от 0.0 до 1.0 (например, 0.1 — это скидка 10%):

- ранняя покупка: скидка 10%;
- покупка в последний момент: без скидки.

Размер скидки должен находиться в диапазоне от 0.0 до 1.0. Некорректное значение необходимо отклонить.

### Расчёт выручки

Система должна уметь суммировать итоговую цену выбранных билетов. Какие билеты попадают в расчёт, определяется условием отбора — оно тоже передаётся как параметр. Используйте эту возможность, чтобы рассчитать:

- фактическую выручку по проданным билетам;
- потенциальную выручку по билетам, которые ещё доступны.

## Этап 3. Добавьте аналитику

Подготовьте несколько сводок по билетам:

1. Подсчитайте количество билетов в каждом состоянии.
2. Найдите самый дорогой из доступных билетов. Если доступных билетов нет, корректно сообщите об этом.
3. Сформируйте краткое описание каждого билета в виде коллекции пар «идентификатор — описание», чтобы по идентификатору можно было быстро найти описание нужного билета.

Описание билета должно включать номер места, категорию, итоговую цену и текущее состояние. Например:

```text
T001: место 1, партер, цена 1500 рублей, доступен
```

## Этап 4. Реализуйте групповое бронирование

Покупатель может захотеть забронировать сразу несколько мест. Такая операция должна выполняться целиком:

1. Найдите все билеты по переданным идентификаторам.
2. Убедитесь, что каждый билет существует.
3. Убедитесь, что каждый билет доступен.
4. Рассчитайте цену каждого билета по выбранному правилу и верните покупателю список рассчитанных цен или общую сумму бронирования.
5. Переведите все билеты в состояние «забронирован».

Если хотя бы один билет не найден или недоступен, бронирование должно завершиться ошибкой. Состояние остальных билетов при этом не должно измениться. Пользователь должен получить сообщение, объясняющее причину отказа.

## Этап 5. Подготовьте отчёт по спектаклю

Итоговый отчёт должен быть удобен для чтения и включать:

- название, дату и место проведения спектакля;
- количество доступных, забронированных, проданных и отменённых билетов;
- общую выручку от проданных билетов;
- количество проданных билетов в каждой категории.

Пример структуры отчёта:

```text
Спектакль: Ревизор
Дата: 20 октября 2026, 19:00
Место: Основная сцена

Доступно: 5
Забронировано: 3
Продано: 7
Отменено: 0

Выручка: 12 100 рублей
Продажи по категориям: партер - 3, балкон - 2, ложа - 2
```

## Дополнительные задания

Выполняйте этот раздел после завершения основной части.

### Составные правила ценообразования

Научите систему выбирать одно из нескольких правил расчёта цены в зависимости от билета. Например, предоставляйте скидку 20% для ложи и 10% для остальных категорий.

### История изменения цены

При каждом изменении базовой стоимости автоматически фиксируйте идентификатор билета, старое и новое значения. Запись может выглядеть так:

```text
Билет T001: цена изменена с 1000 до 1200 рублей
```

### Ограничение числа изменений

Добавьте ограничение на количество изменений состояния одного билета, например не более 5. После достижения лимита система должна отклонять новые изменения. Правила допустимых переходов при этом продолжают действовать.

### Дорогие билеты

Добавьте признак дорогого билета. Билет считается дорогим, если его итоговая цена превышает 2000 рублей. Признак должен вычисляться при первом обращении к нему и запоминаться, чтобы не пересчитываться при каждом запросе.

### Защита данных о выручке

Храните суммарную выручку как отдельное изменяемое свойство в данных о спектакле. Не позволяйте записывать в него отрицательное значение: некорректная попытка должна отклоняться, а факт попытки — фиксироваться, например сообщением в журнале.

- правильно рассчитываются выручка и статистика;
- итоговый отчёт содержит все обязательные сведения;
- решение разделено на понятные части и легко читается.

## Подсказки

Здесь собраны приёмы Kotlin, которые пригодятся на разных этапах. Если что-то незнакомо — сверьтесь с документацией языка: примеры ниже указывают направление, но не обязательны к буквальному повторению.

### Описание данных

- Состояния билета удобно описать закрытой иерархией (`sealed class` или `sealed interface`) — компилятор подскажет, если вы забудете обработать какой-то вариант.
- Категории мест с множителем цены — естественный кандидат на `enum class`: у элементов перечисления могут быть собственные поля.
- Данные о спектакле — простой набор значений, для таких случаев подходит `data class`.

### Функции как параметры

- Условия отбора, действия и правила расчёта удобно передавать лямбдами: `{ ticket -> ... }`.
- Функция может не только принимать функции-параметры, но и возвращать функцию — так устроена операция, создающая правило ценообразования.
- Полезные функции стандартной библиотеки для коллекций: `filter`, `map`, `groupBy`, `sumOf`, `maxByOrNull`, `associate`; для подсчёта элементов по группам — `groupingBy { }.eachCount()`.

### Обработка ошибок

- Результат вида «успех или ошибка» удобно выражать типом `Result`: `Result.success(...)`, `Result.failure(...)`, а оборачивать код — через `runCatching { }`.
- Обрабатывайте результат через `onSuccess` и `onFailure`.

### Дополнительные задания

- Отслеживать изменения свойства помогает `Delegates.observable`, отклонять некорректные значения — `Delegates.vetoable`.
- Отложить вычисление до первого обращения можно через `by lazy { }`.
- Кастомное поведение свойства описывается классом с операторами `getValue` и `setValue`.

Не пытайтесь реализовать всё сразу. После каждого этапа подготовьте несколько примеров и проверьте как успешные, так и ошибочные сценарии.

Полезный порядок работы:

1. Опишите спектакль, билет, категории и состояния.
2. Проверьте расчёт цены и переходы между состояниями.
3. Создайте набор тестовых билетов.
4. Реализуйте поиск и массовые операции.
5. Добавьте правила ценообразования и расчёт выручки.
6. Реализуйте групповое бронирование.
7. Соберите аналитику и итоговый отчёт.
8. Перейдите к дополнительным заданиям.

Главная цель проекта - не только получить работающую программу, но и научиться превращать требования в небольшие проверяемые шаги, заранее продумывать ошибки и отделять правила предметной области от деталей реализации.
